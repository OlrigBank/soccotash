# E02-F03 — Redirect Inbound WhatsApp Replies

## Status

In implementation.

## Parent epic

[E02 — Getting WhatsApp Telephone Messaging Working](./epics/e02-f00-getting-whatsapp-telephone-messaging-working.md)

## Context

Olrig Bank uses its WhatsApp number for transactional booking notifications,
not as a monitored inbox. A guest may nevertheless reply to a notification or
send an unexpected message to that number. Silently accepting the message
could lead the guest to believe that Olrig Bank will read and act on it.

Meta delivers inbound messages and outbound delivery statuses through the same
signed `messages` webhook subscription. An inbound guest message opens the
customer-service window in which an immediate free-form acknowledgement can be
sent without an approved template. The applicable Meta policy must be checked
again before production activation.

This feature is a narrow redirection acknowledgement. It does not introduce a
WhatsApp inbox or two-way guest conversation handling.

## Objective

Send one standard redirection response to an unexpected inbound WhatsApp
message when the sender's normalized telephone number exists in the booking
table, without reading, storing or exposing the guest-authored content.

## Standard response

> Thank you for your message. This WhatsApp number is used for Olrig Bank
> booking notifications only, and incoming messages are not monitored.
>
> For booking queries, please use your private booking chat. For other
> enquiries, please use one of the methods on our Contact page: [Contact-page
> link].

The implementation substitutes the environment-appropriate canonical Contact
page URL. It must not include or derive a private booking URL.

## Proposed implementation

### Recognise inbound messages

- Retain the webhook's exact-byte signature verification, payload limit and
  envelope validation.
- Inspect each valid `messages` change independently for supported delivery
  statuses and inbound messages; an inbound-only payload currently produces an
  empty status list rather than a parser error.
- Extract only the inbound Meta message ID and sender telephone number. Treat
  text, image, audio, video, document, location and other message types alike;
  their content and metadata are not processed.
- Normalize the sender using the existing WhatsApp telephone normalization.
- Consider the sender recognised when that normalized number exists as
  `guest_telephone_e164` in `provisional_bookings`.
- Return `200` for a valid event from an unknown or invalid number, but send
  nothing and reveal nothing.

### Send one redirection acknowledgement

- Add a free-form WhatsApp text sender alongside the existing approved-template
  sender.
- Gate automatic replies behind an independent
  `WHATSAPP_INBOUND_AUTO_REPLY_ENABLED` switch as well as valid Meta provider
  configuration.
- Send the standard response only to the normalized sender number.
- Respond at most once to the same normalized telephone number in any rolling
  24-hour period.
- Start the suppression period after Meta accepts the response. A failed
  attempt may be retried within a defined, bounded retry policy.
- Do not create an email fallback. This acknowledgement is not a transactional
  booking notification.

### Preserve privacy and idempotency

- Record each inbound Meta message ID under a unique constraint so Meta retries
  cannot create duplicate work or responses.
- Enforce the per-number 24-hour rule atomically so concurrent webhook
  deliveries cannot both send.
- Persist only the provider message ID, a recipient hash or mask, the matched
  booking identifier, receipt time, response state and response/error timing.
- Never persist or log message bodies, captions, filenames, media identifiers,
  contact cards, locations or full telephone numbers.
- Use a configured canonical public site URL for the Contact-page link rather
  than trusting the webhook request host.

### Operate safely

- Acknowledge a valid webhook promptly after durable receipt; do not hold the
  Meta response open for slow outbound delivery.
- Use durable bounded processing with retry-safe state transitions rather than
  an untracked background promise.
- Include failed or persistently pending inbound acknowledgements in the
  protected Administration Alerts count and drill-down instructions.
- Disabling inbound automatic replies must not disable delivery-status
  processing for outbound booking notifications.

## Acceptance criteria

1. Existing delivery-status callbacks continue to be processed unchanged.
2. A signed inbound event from a number present in `provisional_bookings`
   durably schedules the standard response and receives a prompt `200`.
3. An unknown or invalid sender receives no response and the webhook still
   returns `200` without revealing booking information.
4. The inbound message body and media metadata are neither stored nor logged.
5. Duplicate and concurrent callbacks for one inbound Meta message result in
   no more than one response.
6. A recognised telephone number receives at most one accepted response in a
   rolling 24-hour period.
7. Text and media messages follow the same content-blind processing path.
8. The Contact link uses the configured canonical public URL and no private
   booking URL is disclosed.
9. A failed response uses bounded retry handling, creates no email fallback and
   becomes visible in Administration Alerts when operator action is required.
10. The independent kill switch prevents automatic replies without affecting
    outbound delivery-status callbacks.

## Test coverage

- Mixed and separate inbound-message and delivery-status webhook payloads.
- Valid, malformed, unknown and normalized UK/international sender numbers.
- Text, media and unsupported inbound message types without content retention.
- Duplicate Meta message IDs and concurrent webhook delivery.
- Atomic rolling 24-hour suppression, including a second booking sharing the
  same telephone number.
- Disabled and misconfigured automatic-reply states.
- Successful provider acceptance, transient failure and terminal failure.
- Canonical Contact URL construction and absence of private booking URLs.
- Administration Alerts counts and instructions for failed acknowledgement
  work.

## Out of scope

- Reading, storing, displaying, searching or moderating inbound message content.
- A shared inbox, conversation history or administrator reply interface.
- Answering booking questions through WhatsApp.
- Downloading or retaining inbound media.
- Email fallback for the redirection acknowledgement.
- Responding to telephone numbers absent from the booking table.
- Marketing, promotional or conversational automated messages.
