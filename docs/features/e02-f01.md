# E02-F01 — Harden WhatsApp Delivery-status Webhooks

## Status

Proposed; ready for implementation.

## Parent epic

[E02 — Getting WhatsApp Telephone Messaging Working](./epics/e02-f00-getting-whatsapp-telephone-messaging-working.md)

## Context

The application already sends booking-update templates through the Meta
WhatsApp Cloud API and exposes `/api/webhooks/whatsapp/` for webhook
verification and outbound-message delivery statuses. The endpoint verifies
Meta's POST signature, deduplicates status events and records `sent`,
`delivered`, `read` and `failed` transitions.

The endpoint is therefore an outbound delivery-status callback, not yet an
inbound guest-conversation service. Before connecting it to Meta in the
development environment, its request handling and regression coverage should
be hardened so acknowledgements are prompt, signatures are checked against
the exact bytes received and status changes remain deterministic.

## Objective

Make the existing Meta delivery-status webhook safe and predictable for a
development-first acceptance test without introducing two-way guest
messaging.

## Proposed implementation

### Verify the exact request

- Read the POST body as bytes and calculate `X-Hub-Signature-256` from those
  original bytes using `WHATSAPP_APP_SECRET`.
- Retain constant-time comparison and reject absent, malformed or invalid
  signatures without parsing or persisting the payload.
- Validate the expected Meta webhook envelope before processing changes,
  including the WhatsApp object and message-status field.
- Apply a documented request-size limit and reject an oversized payload before
  performing unbounded parsing or database work.
- Keep GET subscription verification based on
  `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, with exact challenge echoing and tests for
  missing or incorrect parameters.

### Process status events deterministically

- Parse only supported status callbacks and safely ignore unrelated webhook
  changes.
- Process statuses for the same provider message in Meta timestamp order,
  rather than allowing concurrent database lock acquisition to determine the
  result.
- Define and test monotonic precedence for `sent`, `delivered`, `read` and
  `failed`, including late and duplicate callbacks. A late failure must not
  downgrade a message already confirmed as delivered or read.
- Preserve event-level idempotency so Meta retries cannot duplicate status
  history or trigger email fallback more than once.
- Record enough non-secret diagnostic context to explain ignored or rejected
  events without logging access tokens, verification tokens, signatures,
  message content or telephone numbers.

### Acknowledge Meta promptly

- Complete signature and envelope validation before acknowledging a POST.
- Persist accepted status events reliably, but move potentially slow email
  fallback delivery out of the webhook response path.
- Use the application's established retryable notification processing rather
  than adding an untracked fire-and-forget promise.
- Return a successful acknowledgement for valid, safely accepted callbacks so
  Meta does not retry merely because an email provider was slow or
  unavailable.

### Add endpoint-level coverage

Exercise the actual Astro route, not only helper functions, for:

1. successful GET verification and rejected verification attempts;
2. valid signed POST payloads;
3. missing, malformed and invalid signatures;
4. malformed JSON, unexpected envelopes and oversized bodies;
5. duplicate callbacks;
6. out-of-order `sent`, `delivered`, `read` and `failed` callbacks;
7. batches containing multiple statuses; and
8. a failed WhatsApp delivery scheduling exactly one email fallback without
   delaying the webhook acknowledgement.

## Acceptance criteria

1. Meta can complete GET webhook verification using the configured
   development verification token.
2. POST signatures are calculated from the exact request bytes and compared
   in constant time.
3. Invalid, malformed or oversized requests cause no notification or status
   writes.
4. Duplicate and out-of-order callbacks produce one deterministic,
   non-regressing delivery state.
5. A delivered or read message cannot later become failed because callbacks
   arrived in a different order.
6. A genuine failed delivery schedules email fallback no more than once.
7. Email-provider latency or failure does not hold open an otherwise valid
   Meta webhook request.
8. Logs and stored diagnostics do not expose secrets, signatures, message
   bodies or full telephone numbers.
9. Route-level automated tests cover GET verification, signed POST handling,
   rejection paths, idempotency and ordering.
10. Existing outbound WhatsApp template delivery and consent rules continue to
    pass their regression tests.

## Development acceptance procedure

1. Configure the development Render service with the documented WhatsApp
   variables, keeping `WHATSAPP_DELIVERY_ENABLED=false` while secrets and the
   callback are prepared.
2. Register the development callback URL
   `/api/webhooks/whatsapp/` in the Meta application and complete verification.
3. Run automated route, notification and database tests with synthetic signed
   payloads.
4. Restrict the live acceptance recipient to an authorised development number
   and enable delivery only for the controlled test.
5. Send one approved template and confirm `sent`, `delivered` and `read`
   transitions, then exercise a controlled failure and confirm one email
   fallback.
6. Disable delivery again after the acceptance evidence is captured unless a
   separate production-readiness feature has been approved.

## Out of scope

- Receiving, storing or replying to guest-authored WhatsApp messages.
- A shared inbox, conversation history, media handling or automated replies.
- Enabling WhatsApp delivery in production.
- Changing booking consent rules or allowing arbitrary recipient numbers.
- Creating or approving Meta message templates.

Two-way guest messaging should be specified as a separate feature because it
requires its own privacy, retention, moderation, consent and operational
decisions.
