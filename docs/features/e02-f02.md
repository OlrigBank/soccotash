# E02-F02 — WhatsApp Production Readiness

## Status

Proposed; ready for implementation.

## Parent epic

[E02 — Getting WhatsApp Telephone Messaging Working](./epics/e02-f00-getting-whatsapp-telephone-messaging-working.md)

## Context

E02-F01 proved the outbound Meta WhatsApp path in development from template
submission through `sent`, `delivered` and `read`. A controlled failure also
proved that fallback work is durable, idempotent and processed exactly once.

Production remains disabled. The next step is to turn the development proof
into an explicit operational contract, close the remaining scheduling and
monitoring gaps, and present a documented go/no-go decision. This feature does
not itself authorise activation.

## Objective

Make transactional WhatsApp delivery operationally safe for production and
produce enough evidence for the owner to make a separate, informed activation
decision.

## Proposed implementation

### Production configuration audit

- Confirm each required Meta and application variable exists in the production
  Render service without reading or exposing secret values.
- Confirm the production callback URL, subscribed webhook field, approved
  template names and language match application configuration.
- Verify `WHATSAPP_DELIVERY_ENABLED=false` remains the default and current
  production state throughout readiness work.
- Confirm the production sending number and Meta business assets are owned and
  administered by Olrig Bank.
- Document token rotation, revocation and emergency disable procedures.

### Recipient and consent safeguards

- Reconfirm that only Bookers with active consent for their current normalized
  number are eligible.
- Add a production rollout allowlist or equivalent controlled-recipient guard
  that operates independently of consent and the global kill switch.
- Ensure the first production test cannot send to arbitrary historic or live
  booking numbers.
- Document how consent withdrawal and telephone changes stop later messages.

### Durable fallback operation

- Choose and approve how `npm run process:notification-fallbacks` runs in
  production: a Render Cron Job, an existing trusted scheduler or a dedicated
  worker.
- Configure a bounded invocation interval and retain the authenticated
  maintenance endpoint.
- Confirm expired leases recover after interruption and repeated invocations
  do not duplicate email delivery.
- Define an alert threshold for pending, repeatedly attempted or stale jobs.

Creating a paid Render resource requires explicit approval before it is
provisioned.

### Observability and response

- Provide a privacy-safe operational view or report for recent WhatsApp states
  and fallback jobs without exposing full telephone numbers or message bodies.
- Define alerts or checks for webhook authentication failures, provider
  failures, stale submitted messages and fallback processor failures.
- Document incident response: disable delivery, preserve evidence, continue
  email service, rotate compromised credentials and restore cautiously.
- Define retention expectations for status-event and fallback-job records.

### Controlled production acceptance

- Identify one explicitly authorised recipient and one synthetic booking.
- Keep production delivery disabled until the owner gives a separate go
  decision for the test window.
- Send one approved transactional template, confirm `submitted`, `sent`,
  `delivered` and `read`, and disable delivery again after evidence capture.
- Do not deliberately create a real failed delivery when the already-proven
  synthetic failure path and production configuration checks are sufficient.

## Acceptance criteria

1. Production configuration is complete and recorded as present without secret
   disclosure.
2. The production kill switch remains off until an explicit activation or
   controlled-test decision.
3. A rollout recipient guard prevents delivery to numbers outside the approved
   initial cohort.
4. Consent remains required and bound to the current telephone number.
5. Durable fallback processing has an approved production runner and bounded
   schedule.
6. Stale or repeatedly failing jobs can be detected and investigated without
   accessing message contents.
7. Token rotation, emergency disable and incident recovery are documented.
8. A written go/no-go record identifies residual risks, operating cost and the
   exact production activation steps.
9. Production activation occurs only after a separate explicit owner decision.

## Out of scope

- Two-way guest messaging, inboxes or replies.
- Marketing or promotional WhatsApp messages.
- Importing historic contacts or inferring consent.
- Automatically enabling production delivery when this feature merges.
- Provisioning a paid scheduler without explicit approval.

## Verification required before completion

- Booking lifecycle and PostgreSQL integration tests pass.
- Recipient-guard and kill-switch tests pass.
- Fallback lease recovery, idempotency and stale-job reporting are tested.
- Astro check and production build pass.
- `git diff --check` passes.
- Production readiness evidence contains no secrets, complete telephone
  numbers, message bodies or private booking URLs.
