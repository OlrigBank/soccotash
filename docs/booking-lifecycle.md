# Canonical booking lifecycle

> Generated by `npm run generate:booking-lifecycle-docs` from `site/src/lib/booking/lifecycle.ts`. Do not edit this file by hand.

## Purpose

This document presents the executable rules used to decide whether a booking lifecycle action is allowed. The module is independent of Astro pages, SQL and email delivery so those layers can call one decision API instead of re-implementing policy. An unlisted decision fails closed.

## Statuses

| Status | Label | Blocks dates | Terminal | Legacy | Meaning |
|---|---|---:|---:|---:|---|
| `pending` | Pending request | Yes | No | No | The request is awaiting administrator review. |
| `offered` | Offer published | Yes | No | No | A current offer is available for the Booker to accept or decline. |
| `offer_accepted` | Offer accepted (legacy) | Yes | No | Yes | Legacy compatibility state retained for existing records; new decisions do not enter this state. |
| `payment_pending` | Payment required | Yes | No | No | The offer has been accepted and the required payment has not yet been reported. |
| `payment_reported` | Payment reported | Yes | No | No | Payment has been reported but must still be verified by an administrator. |
| `confirmed` | Confirmed | Yes | No | No | The required payment has been verified and the direct booking is confirmed. |
| `approved` | Approved (legacy) | Yes | No | Yes | Legacy confirmed-equivalent state retained for existing records; new decisions do not enter this state. |
| `declined` | Declined | No | No | No | The Booker declined the current offer; a replacement offer may be published. |
| `cancelled` | Cancelled | No | Yes | No | The booking has been cancelled and no longer blocks its dates. |
| `expired` | Expired | No | No | No | The offer expired; a replacement offer may be published. |

## Decision API

Use `decideBookingTransition({ status, action, actor })` for an allowed/denied result, `assertBookingTransitionAllowed(...)` when denial must stop processing, and `listAllowedBookingTransitions(status, actor)` to discover available controls.

The decision module does not update the database. Processing code must lock the booking, ask the module for a decision, apply it conditionally against the expected source status, write the declared activity event and side effects, and commit atomically.

## Required payment boundary

A Booker payment declaration moves `payment_pending` to `payment_reported`. It does **not** confirm the booking. Only an administrator may verify the report and move `payment_reported` to `confirmed`.

## Rule-change red/green cycle

1. Run `npm run generate:booking-lifecycle-docs` and inspect this document.
2. Run `npm run check:booking-lifecycle-docs` and `npm run test:booking-lifecycle`; both must pass.
3. Express the intended policy change first in `site/tests/booking-lifecycle/expected-transitions.ts`.
4. Run the tests and confirm the changed expectation causes a failure.
5. Change `site/src/lib/booking/lifecycle.ts` to implement the decision.
6. Run the tests until they pass.
7. Regenerate this document and run the documentation check again.

The expected-transition fixture is intentionally separate from the executable model, allowing a test-first policy change to turn the suite red rather than testing the model against itself.
